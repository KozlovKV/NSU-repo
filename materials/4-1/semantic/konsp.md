# 25.09.05
Будем изучать не то что даже семантик вэб, а графы знаний в целом

Классическое устройство вэба нам всем достаточно хоршо знакомо. Достаточно быстро в такой организации вэба была обнаружена проблема - HTML-страницы удобны людям, но не машинам (им надо парсить). Примеры сложных для такого вэба запросов:
- Скрипичный концерт Бетховена китайским оркестром
- Английские рок-музканты, женатые на скандинавках

В этих запросах есть сразу несколько фактов, из которых по итогу поисковик чаще всего цепляется только за один

Решение проблемы достаточно простое по сути - помиомо HTML-страниц хранить набор записей о thing'ах - объектах реального мира, связанных между собой по смыслу. Связи при этом ещ1 будут типизироваться, опять же, по смыслу (формат RDF).

RDF представляет собой триплет: субъект, отношение, объект (subject, predicate, object)

Очевидным образом из этих триплетов собирается направленный граф

Принципы открытых связных данных:
- Для идентификации объектов реального мира нужны уникальные идентификаторы (URI - unified resource identifiers)
- Не просто URI, **HTTP-URI**
- Полезная информация о сущности должна быть представлена в RDF или SPARQL
- По каждой сущности можно перейти к другим сущностям

Пример - [DBPedia](https://www.dbpedia.org/about/)

Есть ещё вот такая красивая штука с картой разных таких [баз данных](https://lod-cloud.net/)

# 25.09.12
Жизненный цикл связных данных:
- Создание связных данных
- Публикация
- Обратная связь
- Изменение

3 этапа при работе со связными данными:
1. Создание данных, присвоение им HTTP URi м выбор типа словарей
2. Связывание данных
3. Публикация

**IRI** - internationalized resource identifier - обобщение URI, в нём ожно использовать любые символы юникод, тогда как в URI только ASCII

URI могут быть разыменованы двумя вариантами:
- Информационные - документы
- Неинформационные - сущности

Получить доступ к RDF-документам (если они есть, конечно) можно несколькими вариантами:
- Непосредственно через URI
  - Надо удостовериться, что RDF существует, поэтому для начала посылается GET-запрос на RDF-документ к основному ресурсу с хэдером на на тип `application/rdf`
  - Если RDF есть, получаем ответ с кодом редиректа и адресом непосредственно URI RDF-документа
- Использоывть хэш-коды RDF-документов, которые хранятся в едином словаре по определённому адресу

Первый способ универсален, но требует редиректа, во втором не нужен редирект, но словарь подойдёт только в случае, когда у нас не так много сущностей

# 25.09.19
**Принцип 3** - при поиске по URI предоставлять полезную информацию в одном из принятых форматов

**RDF** - resource description framework - включается в себя много форматов
- Ссылки должны быть типизируемыми (предикаты)
- Гетерогенно-структурирована
- **RDF 1.0** представляется ориентированным графом с именованными вершинами и рёбрами, также может представляться в виде множества триплетов
- Триплет состоит из субъекта, предиката и объекта. Предикат ведёт от субъекта к объекту => **субъект - всегда ресурс со своим URI (овал)**, а объект может быть как ресурсом, так и литералом - простым свойством (прямоугольник)
  - Literal triplet - триплет с объектом-литералом
  - RDF link - триплет с двумя ресурсами. Могут быть внутренними и внешними (во втором случае связываются ресурсы из разных пространств имён)

А теперь пройдёмся по форматам RDF:
- Самый простой - напрямую все URI для сущностей и типов + литералы:
  - RDF link - `<subject_URI> <predicate_type_URI> <object_URI>`
  - Literal triplet - `<subject_URI> <predicate_type_URI> "value"`
    - После `"value"` может быть доблен тип литерала или язык (`^^<literal_type_URI>`)
- И дальше ещё много форматов - просто посмотри вторую презу короче

---

**Принцип 4** - устанавливать связи RDF на другие сущности

По смыслу связи RDF могут быть:
- Реляционными - связи с другими источниками данных
- Идентичные - указывают на URI для того же объекта реального мира, но в других источниках данных
- Словарные - связи со словарными терминами, используемыми в этих данных
